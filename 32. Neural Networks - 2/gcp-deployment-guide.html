The big picture

Four stages, and this guide walks all four: train & save the model in a notebook → serve it with Flask → push it to GitHub → deploy it on a Google Cloud VM that the whole internet can reach.

Analogy: training is practising past papers. Saving the model is writing down everything you learned. Serving with Flask is opening a help desk where people can ask questions. Deploying to the cloud is moving that help desk into a building the whole world can visit, 24/7.

1Save the trained model from Jupyter

In the training notebook, once the loss has shrunk and the predictions look good, save the learned weights to a file. We save only the state_dict (the learned numbers), not the whole Python object — it's the portable, standard way to ship a model.

Jupytertorch.save(model.state_dict(), "salary_net.pth")   # just the weights

This produces salary_net.pth — a small file (a few KB for our tiny net). The Flask app will rebuild the same SalaryNet class and pour these weights back in, so the server never has to retrain.

Why state_dict and not the whole model? Saving only the weights means the file doesn't depend on your exact folder layout or Python session. Anyone with model.py can recreate the network and load these numbers.

2Set up the Flask app in a virtual environment

Do this on LOCAL your laptop first, to confirm everything runs before touching the cloud. A virtual environment (venv) is a private box of Python packages for just this project, so it never clashes with anything else on your machine.

Your project folder has these files (the app you'll deploy):

FileWhat it does
model.pyDefines the SalaryNet network + a load_model() helper. Shared by notebook and app.
salary_net.pthThe saved, trained weights from Step 1.
app.pyThe Flask web app — loads the model once at startup and serves predictions on port 8080.
requirements.txtThe exact packages needed: torch and flask.
 
LOCALpython3 -m venv venv                       # 1. create the private box
venv/bin/pip install -r requirements.txt    # 2. fill it from the list
venv/bin/python app.py                      # 3. run the app using that box

When you see Running on http://0.0.0.0:8080, open http://localhost:8080 in your browser. You should get the Salary Predictor form. Test the API too:

LOCALcurl -X POST http://localhost:8080/api/predict \
  -H 'Content-Type: application/json' \
  -d '{"experience": 5}'
# -> {"experience": 5, "salary": 65000}
The app listens on 0.0.0.0:8080 (see the last line of app.py). 0.0.0.0 means "accept connections from any network interface" — essential on the cloud, where the request comes from the internet, not from inside the machine.

3Push the project to GitHub

We put the project on GitHub so the cloud VM can simply clone it — no copying files by hand. The trained salary_net.pth is committed too, so the server never retrains.

LOCALgit init
git add model.py app.py requirements.txt salary_net.pth
git commit -m "SalaryNet app"
# create a PUBLIC repo and push (GitHub CLI):
gh repo create SalaryNetApp --public --source=. --push
Keep the venv out of git. Add a .gitignore with venv/ and __pycache__/ — the big virtual-environment folder should never be committed; the VM builds its own fresh one.
Our example repo is https://github.com/Laxminarayen/SalaryNetApp.git — the clone command in Step 6 uses it. When you make your own, swap in your repo URL.

4Create the GCP VM (e2-small) & allow traffic

A Compute Engine VM is a computer you rent from Google, running 24/7 in a data centre. Go to the Google Cloud Console, use the search bar at the top, type VM instances, and click Create instance.

↑ The "Create an instance" screen — pick these exact values, then scroll down and click the blue Create button.
  • Name: anything — e.g. salarynet-vm.
  • Region: pick one near you (asia-south1 = Mumbai) for low latency.
  • Machine type: series E2, type e2-small (2 GB RAM) — plenty for this tiny model, and cheap.
  • Boot disk: Debian or Ubuntu (our commands use apt-get).
  • Under Firewall, tick Allow HTTP traffic and Allow HTTPS traffic.
  • Click Create and wait ~30 seconds for the green tick.
Those tick-boxes only open ports 80 and 443. Our app runs on port 8080, which is not opened by them. We open 8080 ourselves in Step 5 — this is the step most people miss, and the usual reason the site won't load later.

5Open port 8080 & tag the VM

Do this in CLOUD SHELL — the >_ icon at the top-right of the Console. It runs as you, so it's allowed to change firewall rules. (The VM's own SSH terminal is not — see the warning below.)

5a · Create a firewall rule for port 8080

This rule lets anyone on the internet (0.0.0.0/0) reach port 8080 on any VM that carries the network tag salarynet.

CLOUD SHELLgcloud compute firewall-rules create allow-8080 \
  --allow tcp:8080 \
  --target-tags salarynet \
  --source-ranges 0.0.0.0/0

5b · Put the salarynet tag ON the VM

The rule only applies to VMs that carry the tag. A brand-new VM does not have it, so we add it. First list your VMs to find the zone, then tag it.

CLOUD SHELLgcloud compute instances list          # note the ZONE column

gcloud compute instances add-tags salarynet-vm \
  --zone=asia-south1-a --tags=salarynet

You can also do this in the Console UI: VM instances → click your VM → Edit → Network tags → add salarynet → Save.

This is the single most common reason the website won't open. The firewall rule can exist and the app can be running — but with no matching salarynet tag on the VM, Google silently blocks port 8080. Verify the tag landed: 
CLOUD SHELLgcloud compute instances describe salarynet-vm \
  --zone=asia-south1-a --format="value(tags.items)"
# -> salarynet
If you run a gcloud firewall/tag command inside the VM SSH window you'll get "Request had insufficient authentication scopes." The VM isn't allowed to change firewall rules. Use CLOUD SHELL.

6SSH in, install git & venv, clone, run

Back in VM instances, click the SSH button next to your VM. A black terminal window opens — this is VM SSH, running inside the rented computer. Run these one at a time.

SSH-in-browser — salarynet-vm
yourname@salarynet-vm:~$ sudo apt-get update
yourname@salarynet-vm:~$ git clone https://github.com/...
yourname@salarynet-vm:~$ venv/bin/python app.py
* Running on http://0.0.0.0:8080
↑ The in-browser SSH terminal you get from the SSH button. Everything below runs here.

6a · Update the VM & install git + venv

VM SSHsudo apt-get update
sudo apt-get install -y git python3-venv

sudo means "run as administrator"; apt-get update refreshes the list of installable software; then we install git (to clone our repo) and python3-venv (to build the virtual environment).

6b · Clone your repo from GitHub

VM SSHgit clone https://github.com/Laxminarayen/SalaryNetApp.git
cd SalaryNetApp

6c · Build the venv, install packages, run the app

The pip install downloads PyTorch, so give it a minute or two.

VM SSHpython3 -m venv venv
venv/bin/pip install -r requirements.txt
venv/bin/python app.py

When you see Running on http://0.0.0.0:8080, the app is live. Leave this window open — closing it stops the app. Stop the app any time with Ctrl+C.

A harmless "Failed to initialize NumPy" warning may appear — ignore it, the app still works. Before leaving the terminal, you can confirm the app answers locally: curl http://localhost:8080/health should print {"status":"ok"}.

Three things people get wrong here: use http:// not https:// (we set up no certificate); keep the :8080 on the end (browsers hide it otherwise); and use the External IP, not the internal 10.x.x.x one.

8Stop the VM · Troubleshooting

Stop the VM when class is over so it stops costing money: VM instances → tick your VM → Stop. Starting it again later gives a new External IP. (Stopping does not delete anything — your files stay on the disk.)

"The app runs, but the website won't open"

Almost always the firewall tag. Work through these in order:

  1. VM SSH curl http://localhost:8080/health → if it prints {"status":"ok"}, the app is fine; it's a network issue (keep going).
  2. CLOUD SHELL confirm the VM carries the salarynet tag (Step 5b). Missing tag = the usual bug.
  3. CLOUD SHELL confirm the rule exists: gcloud compute firewall-rules describe allow-8080
  4. In the browser: http://, the :8080 suffix, and the External IP.

"Port 8080 is in use by another program"

An older copy of the app is still holding the port. See what it is, then stop it:

VM SSHsudo ss -ltnp 'sport = :8080'     # what is holding 8080?
sudo pkill -9 -f app.py            # if it's python app.py
sudo fuser -k 8080/tcp             # last resort: free the port

"I killed it but it keeps coming back"

A leftover systemd service with Restart=always is relaunching it. Find and remove it:

VM SSHsystemctl list-units --type=service | grep -i -E 'salary|gunicorn'
sudo systemctl stop salarynet
sudo systemctl disable salarynet
sudo rm /etc/systemd/system/salarynet.service
sudo systemctl daemon-reload

"insufficient authentication scopes"

You ran a gcloud firewall/tag command inside VM SSH. Those must run in CLOUD SHELL instead.

Stop the VM when you're done.
