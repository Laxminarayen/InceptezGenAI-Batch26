1.What This App Is

A single-file Flask server that loads the exported model.onnx and classifies uploaded images into the 10 CIFAR-10 classes. It is deliberately built for a tiny, CPU-only EC2 box (e.g. t2.micro, 1 GiB RAM): no PyTorch, no GPU, strict memory limits, and heavy input validation. It serves both a human HTML page (/) and a JSON API (/api/predict).

CIFAR-10-deployment/ ├── app.py # this file ├── requirements.txt # Flask, Pillow, numpy, onnxruntime, gunicorn (NO torch) └── artifacts/ ├── model.onnx # exported by train.ipynb └── classes.json # the 10 label names

2.Imports & Constants

app.py · top 
import json, logging
from pathlib import Path
import numpy as np
import onnxruntime as ort
from flask import Flask, jsonify, render_template_string, request
from PIL import Image, ImageOps, UnidentifiedImageError

BASE_DIR = Path(__file__).resolve().parent
MAX_UPLOAD_MB = 8
MAX_IMAGE_PIXELS = 12_000_000   # guard against decompression bombs on 1 GiB RAM
DEFAULT_MEAN = [0.485, 0.456, 0.406]   # must match train.ipynb
DEFAULT_STD  = [0.229, 0.224, 0.225]
DEFAULT_SIZE = [128, 128]
  • onnxruntime not torch — inference uses ONNX Runtime, which is small and CPU-friendly. PyTorch is never imported in production.
  • render_template_string — the whole HTML page is a Python string in this file (no templates/ folder needed), keeping deployment to a single file + artifacts.
  • BASE_DIR = Path(__file__).resolve().parent — absolute path to the app's folder, so it finds its artifacts regardless of the working directory on EC2.
  • MAX_UPLOAD_MB / MAX_IMAGE_PIXELS — two independent limits: bytes on the wire, and decoded pixels in memory. The pixel cap stops a small file that decompresses into a huge image ("decompression bomb") from exhausting RAM.
  • DEFAULT_MEAN/STD/SIZE — the ImageNet normalization and 128×128 size from training. These are fallbacks; the app prefers values embedded in the artifacts if present.

3.Finding the Artifacts

def find_artifacts():
    for folder in (BASE_DIR / "artifacts", BASE_DIR):
        model = folder / "model.onnx"
        labels = folder / "classes.json"
        if model.is_file() and labels.is_file():
            return model, labels
    raise FileNotFoundError(...)

MODEL_PATH, CLASSES_PATH = find_artifacts()

Looks for model.onnx + classes.json in either artifacts/ or next to app.py — supporting two common layouts. If it can't find both together, it raises a clear error at startup rather than failing on the first request. This runs at import time, so a misconfigured server never starts.

  • Handles two formats — the current notebook writes a plain JSON list of 10 names; a future version might write a dict with labels + preprocessing. The code accepts either (backward/forward compatible).

5.Loading the ONNX Session (CPU-safe)

app.py · ONNX Runtime session 
opts = ort.SessionOptions()
opts.intra_op_num_threads = 1
opts.inter_op_num_threads = 1
opts.execution_mode = ort.ExecutionMode.ORT_SEQUENTIAL
SESSION = ort.InferenceSession(
    str(MODEL_PATH), sess_options=opts, providers=["CPUExecutionProvider"])
  • Thread counts pinned to 1 — a t2.micro has 1 vCPU and little RAM. Letting ONNX Runtime spawn many threads would thrash the box; intra/inter_op_num_threads = 1 and sequential execution keep memory and CPU predictable.
  • providers=["CPUExecutionProvider"] — explicitly CPU-only (no CUDA).
  • Loaded once at startup into the global SESSION, reused for every request.

6.Reading the Model's Real Input Shape

app.py · introspect the graph 
input_info = SESSION.get_inputs()[0]
INPUT_NAME, INPUT_SHAPE = input_info.name, input_info.shape
if len(INPUT_SHAPE) != 4: raise ValueError(...)

if INPUT_SHAPE[1] == 3:
    LAYOUT = "NCHW"; HEIGHT, WIDTH = INPUT_SHAPE[2], INPUT_SHAPE[3]
elif INPUT_SHAPE[3] == 3:
    LAYOUT = "NHWC"; HEIGHT, WIDTH = INPUT_SHAPE[1], INPUT_SHAPE[2]
  • Instead of hardcoding 128 or 224, the app asks the ONNX model what input it expects (get_inputs()[0].shape) and adapts. This prevents the classic "model wants 128 but code sends 224" shape error.
  • NCHW vs NHWC — it detects where the "3" (channels) sits to know the tensor layout: PyTorch exports NCHW (batch, channels, H, W). HEIGHT/WIDTH are read from the model (falling back to 128 if the model declares a dynamic dimension).
  • The INPUT_NAME is reused later when calling SESSION.run.

8.prepare_image() — Preprocessing Parity

app.py · decode → normalize 
def prepare_image(file_storage):
    if file_storage is None or not file_storage.filename:
        raise ValueError("Choose an image to upload ...")
    with Image.open(file_storage.stream) as raw:
        if raw.width * raw.height > MAX_IMAGE_PIXELS:
            raise ValueError("Image exceeds the 12-megapixel safety limit.")
        raw.seek(0)
        image = ImageOps.exif_transpose(raw)                 # honour EXIF rotation
        if image.mode in ("RGBA", "LA") or ...:
            # composite transparency on WHITE, not black
            rgba = image.convert("RGBA")
            background = Image.new("RGBA", rgba.size, (255,255,255,255))
            image = Image.alpha_composite(background, rgba).convert("RGB")
        else:
            image = image.convert("RGB")
        image = image.resize((WIDTH, HEIGHT), resample=Image.Resampling.BILINEAR)
        pixels = np.asarray(image, dtype=np.float32) / 255.0

    pixels = (pixels - MEAN) / STD                           # same normalization as training
    if LAYOUT == "NCHW":
        pixels = np.transpose(pixels, (2,0,1))               # HWC → CHW
    batch = np.ascontiguousarray(pixels[None, ...], dtype=np.float32)  # add batch dim
    return batch

Every step here exists to make the server's input byte-for-byte equivalent to what the model saw in training:

  • Pixel-count guard — reject anything over 12 MP before decoding fully.
  • ImageOps.exif_transpose — phone photos store rotation in EXIF; this applies it so a sideways photo is classified upright.
  • Transparency → white — PNGs with alpha are composited onto white (not the implicit black), which matches how most training photos look.
  • convert("RGB") — force 3 channels (handles greyscale/RGBA).
  • resize((WIDTH, HEIGHT), BILINEAR) — same size and interpolation family as transforms.Resize in training.
  • /255 then (pixels - MEAN) / STD — scale to 0–1 and apply the identical ImageNet normalization.
  • transpose(2,0,1) — NumPy images are H×W×C; the model wants C×H×W (NCHW), so reorder the axes.
  • pixels[None, ...] — add the batch dimension → shape [1, 3, H, W]. ascontiguousarray ensures a clean memory layout for ONNX Runtime.

9.predict() — Inference & Softmax

app.py · run the model 
def predict(file_storage):
    batch = prepare_image(file_storage)
    for got, expected in zip(batch.shape, INPUT_SHAPE):   # shape guard
        if isinstance(expected, int) and got != expected:
            raise RuntimeError(f"Preprocessing produced {batch.shape}, ONNX expects {INPUT_SHAPE}")
    raw = SESSION.run(None, {INPUT_NAME: batch})[0]
    logits = np.asarray(raw, dtype=np.float64).reshape(-1)
    exps = np.exp(logits - logits.max())          # stable softmax
    scores = exps / exps.sum()
    top = np.argsort(scores)[::-1][:3]              # top-3 classes
    return [{"label": CLASS_NAMES[int(i)],
             "confidence": round(float(scores[i]*100), 2)} for i in top]
  • Shape guard — double-checks the preprocessed batch matches the ONNX input before running, turning a cryptic runtime crash into a clear message.
  • SESSION.run(None, {INPUT_NAME: batch}) — the actual inference call; None means "return all outputs". [0] grabs the logits tensor.
  • np.exp(logits - logits.max()) — the numerically stable softmax: subtracting the max before exponentiating avoids overflow. (The model outputs raw logits, like in training; softmax here just turns them into readable probabilities.)
  • np.argsort(...)[::-1][:3] — indices of the top-3 scores, highest first, mapped to CLASS_NAMES with a rounded percentage.

10.Routes & Running

app.py · endpoints 
@app.get("/")
def index(): return render_page()

@app.post("/")
def predict_html():
    try:    return render_page(predictions=predict(request.files.get("image")))
    except ValueError as exc:   return render_page(error=str(exc)), 400
    except Exception:          return render_page(error="Inference failed ..."), 500

@app.post("/api/predict")
def predict_api(): ...        # same logic, returns JSON

@app.get("/health")
def health(): ...             # status + model input shape + classes

@app.errorhandler(413)
def too_large(_exc): ...        # friendly "upload too large" message

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000, debug=False)
  • @app.get("/") vs @app.post("/") — GET shows the empty form; POST handles the uploaded image.
  • Layered error handling — a ValueError (bad/missing image) returns 400 with the message; any other exception is logged and returns a generic 500 (never leak internals to users).
  • /api/predict — the same prediction logic but returns JSON, for programmatic callers.
  • /health — a monitoring endpoint reporting status, the model's input shape, and the class list — handy for load balancers and debugging on EC2.
  • @app.errorhandler(413) — Flask raises 413 when an upload exceeds MAX_CONTENT_LENGTH; this returns a friendly message (JSON for API paths, HTML otherwise).
  • host="0.0.0.0", port=8000, debug=False — bind to all interfaces so the instance's public IP can reach it, on port 8000, with debug off (never run the debugger on a public server). In production you front this with gunicorn; the built-in app.run is for quick testing.
Why ONNX + these guards matter on EC2. The whole design assumes a cheap, 1 GiB, CPU-only box: ONNX Runtime instead of PyTorch (smaller, no CUDA), single-threaded sessions, pixel/upload caps, and loading everything once at startup. That's what lets a real deep-learning model serve on an instance that costs cents.

In one paragraph

app.py loads the exported model.onnx + classes.json once at startup (failing fast if missing or invalid), reads the model's actual input shape so preprocessing can't drift, and configures ONNX Runtime for a 1-vCPU box. For each upload it decodes defensively (EXIF rotation, transparency-on-white, size caps), resizes and normalizes identically to training, runs inference, applies a stable softmax, and returns the top-3 classes — over an HTML page, a JSON API, and a health check. It's the production half of the training notebook: PyTorch-free, memory-safe, and ready for EC2.
